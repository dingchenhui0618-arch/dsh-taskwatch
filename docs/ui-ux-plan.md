## 0. 三问结论（先看这段）

**1) 有没有现成的？有，而且比预期多。**

| 可复用的东西 | 在哪 | 价值 |
|---|---|---|
| 客户端 **395 个主题令牌的真值** | 从 `D:\.deepseek\resources\app.asar` 里挖出（附录 A） | 手机页可以**用同一套变量名**，不是我照着感觉调色 |
| 客户端**自带的折叠样式** | asar 里的 `compactionRow[data-expanded]`、`compactionButton`、`_3GBCTG_summary[data-streaming]` | **"内容放不下"的官方解法**，直接对标 |
| 现有 `lib/page.html` | 36KB 单文件、零依赖、已验证的流式/工具渲染逻辑 | 换皮即可，不重写渲染管线 |
| 中继已有的 cookie 机制 | `Set-Cookie: tw=…; HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000` | 登录改造的基座 |
| 现有契约测试 | `scripts/check-bundle.mjs`，56 项 | 回归有兜底 |

**2) 最省力的路径：原地重构现有单文件页。**
对比过三条路，放弃了两条：

- ✅ **A. 原地重构**（选它）：换设计令牌层 → 补折叠/溢出 → 改登录。保留已被验证的 SSE 流式、工具卡片、会话抽屉逻辑，风险最小。
- ❌ B. 引入 React/Vue 重写：与"单文件、零依赖、Service Worker 友好"的现状直接冲突；打包产物会让 SW 缓存策略复杂化，收益只有"写起来舒服"。
- ❌ C. 直接复用客户端组件：客户端 UI 跑在 Electron + Cordis client half 里，搬不进一个独立 PWA。

**放弃的**：主题编辑器、多语言、完整 Markdown 渲染器（只做最小集：粗体/代码/列表/链接）。

**3) 怎么算做完了？** 见 §5 的 6 条验收标准。

## 2. UI 改造

### 2.1 设计令牌层（P0，其余都建在它上面）

做一份 `tokens.css` 内联进 `page.html`，**变量名与客户端一致**，明暗两套值：

```css
:root {
  --dsw-alias-label-primary:   #0f1115;
  --dsw-alias-label-secondary: #61666b;
  --dsw-alias-label-tertiary:  #81858c;
  --dsw-alias-border-l1:       #0000000a;
  --dsw-alias-border-l2:       #0000001a;
  --dsw-alias-brand-primary:   #4176e6;
  --dsw-alias-bg-base:         #ffffff;
  --dsw-alias-bg-layer-1:      #f7f8f9;
  /* …其余按附录 A 抄全 */
}
[data-theme='dark'] {
  --dsw-alias-label-primary:   #f9fafb;
  --dsw-alias-label-secondary: #cfd3d6;
  --dsw-alias-label-tertiary:  #adb2b8;
  --dsw-alias-border-l1:       #ffffff0f;
  --dsw-alias-border-l2:       #ffffff1f;
  --dsw-alias-bg-base:         #0f1115;
  /* … */
}
```

**收益**：这不是"看起来像"，而是**同一套变量名**。客户端以后调主题，手机页改一处值就跟着变。

### 2.2 信息架构（贴近客户端 + 手机习惯）

- **顶栏**：会话标题（单行省略） + 状态胶囊（`运行中 N` / `等你回复`） + 溢出菜单
- **消息流**：用户消息右对齐气泡；助手消息左对齐全文（贴合客户端布局），块间用间距而非气泡
- **工具调用**：**折叠成一行** —— 抄客户端的 `compactionRow`：吸顶摘要行 + 点击 `data-expanded` 展开 + 流式中用 `mask-image` 渐隐
- **思考过程**：默认折叠，摘要一行
- **输入框**：自增高（上限 ~6 行）、发送/停止同一键位切换、附件入口
- **会话列表**：底部抽屉 + 搜索框（现在是抽屉但没搜索）
- **状态面板**：从"另一个页面"降级为**消息流里的可展开卡片**，避免两个页面来回跳

### 2.3 溢出策略（逐条，可验收）

| 场景 | 处理 | 参考来源 |
|---|---|---|
| 超长回复 | 折叠 + 「展开」+ 展开后吸顶小标题 | 客户端 `compactionRow` |
| 长命令 / 长输出 | 代码块内滚动（`max-height`）+ 右上角复制 | 豆包/DeepSeek 手机端 |
| 连续多个工具调用 | 折叠成一行「N 个步骤」，展开成时间线 | 客户端 |
| 超长会话标题 | 单行 `text-overflow: ellipsis` | 客户端 `summaryText` |
| 宽表格 / 长 URL | 横向滚动，不撑破布局 | 通用 |
| 输入超长文本 | 自增高到上限后内部滚动 | DeepSeek 手机端 |
| 新消息在下方 | 悬浮「回到底部」+ 未读计数 | 豆包手机端 |
| 流式输出中 | 尾部渐隐遮罩 | 客户端 `mask-image` |

## 3. 登录改造

### 现状的三个痛点

1. 手机上要输**两个**东西：nginx basic auth 用户名密码 + 带令牌的地址；
2. **iOS 会把 basic auth 凭据缓存住，输错了不再重问**，直接 401（这正是 2026-10-08 那次故障的根因，已记进 ACCESS.md）；
3. 30 天 cookie **不会续期**，到点就掉，得重来一遍。

### 3.1 滑动续期（必做，改动最小）

每次校验通过的请求都重发一次 cookie（刷新 `Max-Age`）。
**效果：只要还在用，就不会掉线。** 中继侧约 2 行。

### 3.2 配对码登录（新增，推荐）

把"抄一个 64 位 URL"变成"输 6 个数字"：

1. 桌面侧（插件面板）显示一个 **6 位配对码**，TTL 2 分钟，最多 5 次尝试
2. 手机打开 `/taskwatch/pair`，输码
3. 服务端校验后下发 30 天 cookie → 完成

不用输 URL、不用输密码、不用碰 basic auth 对话框。

### 3.3 basic auth 的去留（**需要你定，这是唯一的分叉**）

**事实**（我实测过，不是推断）：
- 中继的令牌是 256 位随机 + `HttpOnly` cookie，**比共享密码更强**，而且能按设备吊销；
- 没令牌的请求**一律 401**，包括静态文件（`sw.js` 无 cookie 也是 401）；
- basic auth 对 iOS 的 service worker 与 manifest 请求**不生效**（这次故障根因），且输错后不重问。

| 选项 | 说明 | 代价 |
|---|---|---|
| **(a) 去掉 basic auth**（我推荐） | 只留 TLS + 令牌层。体验最顺，安全性反而更清晰（凭据更强、可吊销、无缓存坑） | 少一层"挡住无差别扫描"的门；但没令牌照样 401 |
| (b) 维持现状 | basic auth 保留，只放行 4 个静态文件（2026-10-08 已做） | 手机上仍会遇到"输错不重问"，配对码也用不了 |
| (c) 折中 | 配对码路径放在 basic auth 之外，其余保留 | 多一条"例外路径"，规则变多，但保留双层 |

**我倾向 (a)**：现在的三层里，basic auth 恰恰是**唯一在制造故障**、且**不提供更强保证**的那一层。

## 5. 验收标准（6 条）

1. 手机上一眼看出：**有几个任务在跑、有没有事等你回**（不需要点进去）
2. 能直接对话、逐字回复、看到工具进度、能停止
3. **明暗两套配色与客户端同源**（用同一组变量名与值），跟随系统
4. 长内容不撑破布局：§2.3 的 8 类场景**每类都有明确且可点开查看**的溢出策略
5. 登录：**手机上不需要输入任何密码**，且日常使用不会无故掉线
6. `scripts/check-bundle.mjs` **全绿**，且新增行为都有对应断言（从 56 项起往上加）
